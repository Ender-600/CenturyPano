# 真实行走与手机视角

生成后端、Google 历史全景流程和 Spark 三维显示继续使用原有代码。已加载的生成世界支持两种真实行走输入：`mobile/ios` 与 `mobile/android` 原生客户端用 ARKit／ARCore 的视觉惯性追踪获取位置和朝向；普通 Safari／Chrome 可用 GPS 经度、纬度变化近似跟随室外步行，并继续独立使用方向传感器转动视角。设置中的自动模式在原生客户端优先使用 AR，在浏览器使用 GPS，也可明确选择行走方式。

GPS 适合室外、定位较好的场景，不能提供 AR 的细小位移追踪。浏览器定位可能来自 GPS 或网络，`watchPosition` 不承诺固定更新频率；请求高精度也不保证得到高精度。页面显示定位精度和跟随状态，实际延迟与误差需要真机测量。[W3C Geolocation](https://www.w3.org/TR/geolocation/)

## 竖屏环顾

Safari 的 `webkitCompassHeading` 只用于建立一次北向参照，且要求手机接近水平、精度有效。之后保持固定的北向偏移，使用完整的 `alpha/beta/gamma` 相对姿态四元数跟随俯仰、左右转头和倾斜，不再每帧用指南针覆盖姿态角。优先使用相对方向事件；只有绝对方向事件的设备仍依赖其系统融合，不能保证完全消除磁场干扰。[W3C 方向事件](https://www.w3.org/TR/orientation-event/#choice-of-reference-coordinate-system)

可以直接竖着手机开启 motion，画面立即按相对姿态跟随。若尚无北向参照，短暂放平手机获取指南针，然后重新竖起。后取得的北向参照不让正在跟随的画面突然转向；用「Align heading」对齐同一地标。界面与 GPS 使用的是初始北向参照加当前姿态推导出的镜头方位，手动对齐只改变虚拟视图，不修改真实镜头方位。指南针初始化误差和陀螺仪漂移仍需现场校准。

## 坐标与距离

原生包输出右手、+Y 向上、以米为单位的位置，以及按屏幕方向校正的后摄朝向。首个可靠帧记录现实起点；当前虚拟相机位置是虚拟起点。只校准水平朝向，使重力方向保持一致。

```
虚拟位置 = 虚拟起点 + 模型单位/米 × 朝向校准旋转 ×（当前真实位置 − 真实起点）
虚拟朝向 = 朝向校准旋转 × 当前后摄朝向
```

GPS 模式把相对起点的经纬度变化换算为东、北方向的米制水平位移，再通过固定的水平朝向映射到世界；保持当前相机高度。启用时使用当前可靠指南针的镜头朝向，或由用户输入镜头所指方向的已知地理方位，与当前虚拟视角对齐。这个映射在本次跟随中保持不变。生成世界没有经过地理朝向配准，不能直接假定它的前方就是北方；指南针本身仍可能有磁偏角和干扰。

两种模式的位移都不沿手机当前视线累加。因此原地转手机不平移，边向前走边侧看时位置仍沿真实行进方向变化。GPS 只控制平移，手机俯仰、倾斜和转动继续由现有方向跟随控制；GPS 的行进 `heading` 不作为镜头朝向。每帧在手机本地渲染，不会重新调用图像生成或 Marble。

若查看器已应用提供方米制比例，移动使用每米一个场景单位；比例与地面高度独立处理，有有效比例但无地面高度时仍可按米移动，界面标明地面高度未校准。这仍不证明 AI 世界和现场地物完全一致。缺少尺度元数据时，用户需要指定比例，或在三维场景中选两个点、输入这两点的真实间距。两点测量直接使用 Spark 对实际 splats 的光线求交，取点失败不会猜测深度。手动测量只能校准统一比例，无法修复生成几何的局部形变，也不能自动找回历史建筑的绝对地理位置。

## 运行流程

1. 用手机 Safari／Chrome 或已安装的 CenturyPano 原生客户端打开 HTTPS 演示链接。独立演示访问码可以放在原有 `#access=` 片段中，不需要把服务商密钥写进手机工程。
2. 等待已生成的世界加载，点击画面上的「Set up GPS walking」进入行走设置；先检查尺度，必要时完成两点校准。全景照片只能环视，不能开启位置跟随。「Enable motion」只开启方向跟随，不会开启位移。
3. 用拖动调整虚拟起点和观察方向，保持手机朝向选定的实际方向。GPS 模式先开启转动跟随，短暂放平手机建立北向参照，再竖起手机；完成地标朝向对齐后启用行走。没有可靠指南针时，输入当前镜头朝向的已知地理方位。启动时配对同一姿态样本的真实、虚拟方向，不把画面平滑造成的延迟写进位移映射。不要把行进方向当作手机镜头方向。
4. GPS 模式允许位置权限，等精度合适的定位建立起点后开始跟随；精度筛选、抖动过滤与画面插值减少跳动，但小于定位噪声的步幅可能延后体现。原生模式允许相机权限、等待空间追踪稳定；相机图像只在本机用于追踪，桥接只传位置、朝向和状态。
5. GPS 短暂精度下降或临时定位失败时保持当前位置，在上次可靠定位后的 20 秒内收到新的可靠定位可继续；坏定位不会延长等待期限。超时、跳点、权限丢失、AR 失跟或离开前台后冻结位移，需要明确重设起点，不自动补走后台的路程。切换世界或停止行走后结束本次跟随。三维行走期间不自动更换世界。用户另外开启「Prepare ahead as you walk」后，可在后台准备前方历史全景，并在全景视图到点切换；这不提交新的三维世界生成，详见 [预测步行](PREDICTIVE_WALKING.md)。

GPS 的移动阈值为 `max(1.5 米, 0.35 × (上次移动目标精度 + 新定位精度))`。例如精度均为 ±10 米时，约需累计 7 米的位置变化才更新目标；小步会累积，但也可能被噪声覆盖。画面显示当前精度、距离起点的位移，以及「已观测位移 / 移动阈值」，帮助区分未启用、等待定位和未超过阈值。不会通过降低噪声阈值或沿视线猜测步幅伪造精确行走。

行走中开始手动校准方向（包括开启 motion 后拖动视图）会停止 GPS 跟随；完成对齐后重新启用行走，建立新的方向映射。正常转动手机环顾不会改变位移映射。

开始、停止跟随由页面交互控制；原生相机仅在 AR 模式启用。GPS 近似跟随与原生空间追踪有独立状态提示，不能同时驱动位置。GPS 不使用加速度双积分或步数推算距离，不承诺逐步、厘米级或室内实时定位。

## 验收边界

- 2026-09-12 竖屏与 GPS 修复：`node --test tests/test_world_*.mjs` 174 项通过，`git diff --check` 通过。现有本地网关已返回新版脚本。浏览器视觉检查被 Chrome 的 `ERR_BLOCKED_BY_CLIENT` 阻断；本次未完成视觉布局或 iPhone Safari 实体传感器验收。
- 本地数学与模拟事件测试可验证米制位移的比例换算、GPS 东北方向映射、侧看时的独立平移、纯转动、定位质量筛选、重设起点、陈旧／乱序数据丢弃，以及失跟冻结。
- 模拟器可以检查网页加载、桥接、设置与不支持 AR 的提示，不能证明真实摄像头追踪精度。
- 实体手机验收仍待完成。GPS 需要在开阔室外检查静止漂移、已知距离往返、侧向与后退行走、指南针对齐、定位变差和后台恢复，记录延迟与距离误差。AR 需要在有纹理、光线正常的小范围现场试走，检查前进和后退、原地转动、边走边侧看、横竖屏、遮住摄像头、切到后台和重新开始。
- 生成场景的可用范围和历史几何可能与现场不同；不把生成模型的碰撞面当成现实障碍物。此版本只映射位姿，不保证建筑逐像素对齐或长距离无漂移。
